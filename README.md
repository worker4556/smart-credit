# Smart Credit — «Маршрут к одобрению»

Умный кредитный кабинет предпринимателя — прототип цифрового кредитного конвейера для малого и микробизнеса (Альфа-Хак 2026).

Предприниматель описывает задачу, заранее видит реалистичную сумму и полную стоимость в рублях, подаёт заявку и понимает
каждый следующий шаг. Если нужную сумму сейчас получить нельзя, он получает маршрут: что мешает, что сделать и примерно
когда пробовать снова. Банк обрабатывает ту же заявку по тем же правилам и вручную разбирает только исключения.

## Для жюри

### Запуск

Нужны Docker Desktop (Windows, macOS) или Docker Engine с Compose (Linux), **8 ГБ оперативной памяти** и **~8 ГБ
свободного места** на диске. Видеокарта и интернет после загрузки образов не нужны. Всё, что нужно для работы,
включая языковую модель, уже лежит внутри образов.

**Быстрый запуск — готовые образы** (GitHub собирает их автоматически, под Windows/Linux и Mac):
```bash
git clone <адрес репозитория> smart-credit && cd smart-credit
cp .env.example .env
docker compose pull
docker compose up
```

**Запасной путь — собрать из исходников** (дольше, нужен интернет для зависимостей и модели):
```bash
docker compose up --build
```

Откройте **http://localhost:3000**. Языковая модель с открытыми весами (`qwen3:1.7b`) вшита в образ `llm` и готова
сразу после запуска; она только пересказывает факты, посчитанные правилами, и ничего не решает.
Всё вместе занимает около 3 ГБ памяти.

### Тестовые учётные записи

Пароль у всех — `demo`. У каждого клиента своя компания и свой ИНН.

| Логин | Кто | Что покажет |
|---|---|---|
| `p1` | Ольга, ИП, кофейня | одобрение: 850 000 ₽ на 24 мес., 43 261 ₽ в месяц, полная стоимость 196 774 ₽ |
| `p2` | ООО «Полка», маркетплейсы | сумма больше 2 млн → у специалиста → иные условия 2 850 000 ₽ |
| `p3` | Тимур, ИП, автосервис | слабая предоценка → отказ из-за налогового долга → маршрут ~3 мес. и пересчёт |
| `p4` | Марина, ИП, студия маникюра | отказ по кредитной истории → честное «~8 мес., ускорить нельзя» |
| `p5` | Андрей, ИП, стройматериалы | «нужны данные» → загрузка выписки → одобрен овердрафт 300 000 ₽ |
| `zsk` | ООО с «красным» уровнем ЗСК | приостановка по 115-ФЗ — некредитная причина, маршрута нет |
| `specialist` | кредитный специалист | очередь, карточка заявки с факторами и лимитами, решение с кодом причины |
| `admin` | ведущий демо | все заявки, сброс демо-данных, статус системы и модели |

### Сценарий проверки (5–7 минут)

1. **`p1`** — опишите задачу, пройдите шаги, посмотрите предоценку и «Погоду», отправьте → одобрение, подписание и выдача (демо).
2. **`p2`** — отправьте 3 000 000 ₽ на 18 мес. → заявка у специалиста. Войдите как **`specialist`** → решение «иные условия» → снова `p2`: «хотели 3 млн — можем 2,85 млн».
3. **`p3`** — предоценка покажет низкий шанс; отправьте → отказ с причиной. Откройте маршрут, отметьте шаги, нажмите «Пересчитать», спросите помощника «почему отказали?» и «что такое сальдо ЕНС?».

## Как внедрить в банке

Скоринг здесь — явная балльная карта на правилах (`ml/config/policy.yaml`), а не «чёрный ящик»: так требуют
объяснимость для клиента и прослеживаемость решений для специалиста. Веса подобраны под синтетические данные; на
синтетике карта различает заёмщиков с Gini 0,46 и стабильна ([docs/model-validation.md](docs/model-validation.md)).

| Что банк меняет | Что остаётся как есть |
|---|---|
| Веса, пороги, продукты и ставки — в `ml/config/*.yaml`, без правки кода | Маршрут к одобрению: шаги клиента, сроки, «ускорить нельзя», пересчёт |
| Калибровка: `python -m validation.run` на своей истории заявок вместо синтетики → предложенные веса | Единый справочник причин: код → текст клиенту → шаг → срок |
| Моки реестров и БКИ → реальные интеграции в бэкенде | Объяснения и помощник на локальной LLM с проверкой каждого ответа; 115-ФЗ — только шаблон |
| Модель LLM — любая с открытыми весами (`OLLAMA_MODEL`) | Одна модель для предоценки, решения и маршрута: прогноз не расходится с решением |

Для эксплуатации: аудит каждого решения (версия политики, хэш входа, время), метрики Prometheus `GET ml:8001/metrics`,
сквозной `X-Request-ID`, служебный токен между бэкендом и ML (`ML_SERVICE_TOKEN`), healthcheck у каждого сервиса.

## Как работаем

1. `git pull --rebase` перед началом работы и перед каждым пушем.
2. Каждый работает в своей папке; общие файлы (`docker-compose.yml`, `docs/`) меняем, предупредив команду.
3. Изменения API — сначала в `docs/api-contract.md`, потом в коде.
4. Рабочие материалы команды (дизайн, планы, задания, выдержки из документов аналитиков) — в [docs/team/](docs/team/README.md); это не часть сдачи.
