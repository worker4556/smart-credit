# Варианты использования (Use Cases) — «Маршрут к одобрению»
 
**Продукт.** Умный кредитный кабинет предпринимателя, MVP «Маршрут к одобрению».
* Варианты использования в этом документе описаны по модели Алистера Кобёрна из книги Writing Effective Use Cases. Это самый распространённый в бизнес- и системном анализе способ писать use cases текстом.

### Заинтересованные лица и их интересы
 
| Заинтересованное лицо | Интерес |
| --- | --- |
| Предприниматель | Понять шанс, сумму и стоимость до подачи, не испортив кредитную историю. Получить понятную причину и выход вместо тупика |
| Банк | Меньше заведомо неодобряемых заявок у андеррайтера, прослеживаемые решения, отказник возвращается в этот же банк |
| Кредитный специалист | Видеть причину попадания и готовое досье, не перепроверять очевидное |
| Комплаенс банка | Не раскрывать внутренние алгоритмы, не обещать одобрение, не смешивать 115-ФЗ с кредитным решением |
| Банк России (поведенческий надзор) | Нет вводящих в заблуждение формулировок «одобрено» до решения |
| Недобросовестный заявитель *(негативное)* | Завысить выручку, скрыть просрочку, «подогнать» данные под порог. Защита: сверка выручки со счётом (BR-07), проверка БКИ после подачи (UC-03, 2б), решение по проверенным данным |

## 4. Бизнес-правила
 
Все значения — демонстрационные допущения команды из `ml/config/policy.yaml`, а не данные банка.
 
| ID | Правило |
| --- | --- |
| **BR-01** | **Предоценка.** Считается без запроса в БКИ. Данные о владельце — со слов клиента и помечены «проверим после подачи»; ответ «были просрочки» учитывается как просрочка до 30 дней. Действует 30 дней, затем пересчитывается. Подпись дословно: «Это оценка по текущим данным, а не решение банка. Действует 30 дней.» Слово «одобрено» до экрана решения не используется |
| **BR-02** | **Одна модель.** Предоценка, решение, причины и маршрут считаются одним движком по одной политике. Шанс предоценки соответствует ожидаемому исходу: высокий — одобрение, средний — иные условия, низкий — отказ |
| **BR-03** | **Продукты.** Оборотный кредит: 100 000–3 000 000 ₽ (до 5 000 000 ₽ с поручителем), 3–36 мес., ставка 20%, комиссия 1%, лимит — наименьшее из трёх ограничений: 1,5 × средний оборот; 3 × оборот − текущий долг; платёж не больше 20% оборота за вычетом текущих платежей. Овердрафт: 50 000–3 000 000 ₽, 12 мес., ставка 22%, лимит до 40% среднего оборота за 6 мес., стоимость — проценты на использованный остаток плюс комиссия 1% за установку, без аннуитета |
| **BR-04** | **Скоринг.** 9 факторов, 100 баллов. Слой «бизнес» — 75: регулярность оборотов 20, долговая нагрузка 15, возраст бизнеса 10, сумма к обороту 10, отрасль 8, суды и ФССП 7, срок РКО 5. Слой «владелец» — 25: кредитная история 15, личная нагрузка 10; загрузка кредиток от 50% снимает 8 баллов |
| **BR-05** | **Стоп-факторы.** Налоговый долг больше 500 ₽ (`S_TAX`); бизнес меньше 3 мес. (`S_AGE`); просрочка 90+ дней за 12 мес. (`S_90_12`); текущая просрочка (`S_OVERDUE`); блокировка счёта ФНС (`S_FNS_BLOCK`); иск о взыскании (`S_LAWSUIT`). Постоянные: ликвидация (`S_INACTIVE`), банкротство (`S_BANKRUPTCY`), отрасль не кредитуется (`S_INDUSTRY`) |
| **BR-06** | **Решение — по порядку.** 1) 115-ФЗ (BR-10). 2) Нужны данные (BR-07). 3) Стоп-фактор → `REJECTED`. 4) 70+ баллов и лимит не меньше суммы → `APPROVED`. 5) 70+ баллов, лимит меньше суммы → `COUNTER_OFFER`: другой срок на ту же сумму или меньшая сумма, причина — что держит лимит (например, `L_TURNOVER`). 6) 60–69 баллов → `COUNTER_OFFER`, 75% лимита, ставка +2 п.п.; 50–59 → 50% лимита, +4 п.п.; причина `R_RISK_PRICE`. 7) Меньше 50 баллов или доступная сумма ниже минимума продукта → `REJECTED` |
| **BR-07** | **Нужны данные.** Заявленная выручка выше оборота по счёту больше чем на 30% (`D_MISMATCH`) или нет обязательного документа (`D_DOC`) → `INFO_REQUESTED`. Срок ответа — 14 дней |
| **BR-08** | **Триггеры специалиста.** `AMOUNT_ABOVE_2M` — сумма больше 2 000 000 ₽; `BORDERLINE_SCORE` — 50–59 баллов без стопов; `MISMATCH_UNRESOLVED` — расхождение не снято после выписки; `CLIENT_DISPUTE` — клиент оспорил решение; `ML_UNAVAILABLE` — движок недоступен после трёх попыток. Не применяются к `SUSPENDED_115FZ` и `INFO_REQUESTED`. Решение системы при этом становится рекомендацией |
| **BR-09** | **Причины.** Единый справочник `reasons.yaml` для клиента, специалиста и маршрута. Клиент видит сработавший стоп-фактор и до четырёх факторов с наибольшим недобором, первая причина — главная. Решение специалиста сохраняется только с кодом из справочника |
| **BR-10** | **115-ФЗ.** Уровень ЗСК запрашивается только после подачи. Красный уровень → `SUSPENDED_115FZ`, код `Z_115` вне кредитных причин. Текст только шаблонный: «Заявка приостановлена из-за проверки по 115-ФЗ. Это не оценка вашей кредитоспособности.» Маршрут не строится (`NO_ROUTE`) |
| **BR-11** | **Языковая модель.** Только разбирает фразу клиента и пересказывает посчитанное. Если в её тексте есть числа или коды, которых не было на входе, обещания или «одобрено» до решения — показывается шаблон. Без модели всё работает на шаблонах |
| **BR-12** | **Маршрут.** Стоп-фактор всегда первый шаг: вклад +0, без него маршрут не двигается. Шаги, меняющие кредитную историю, учитывают обновление БКИ за 2 рабочих дня. Горизонт — не больше 24 мес. Пересчёт не создаёт заявку и не обращается в БКИ. Подпись дословно: «Это ориентир при текущем темпе, а не обещание одобрения.» |
| **BR-13** | **«Готов к подаче».** Маршрут получает статус `READY`, когда нет стоп-факторов, оценка 70+ баллов и лимит не меньше выбранной суммы |
| **BR-14** | **Сроки.** `APPROVED` и `COUNTER_OFFER` — 30 дней, `INFO_REQUESTED` — 14 дней; по истечении → `EXPIRED` |
| **BR-15** | **Внутри продукта.** Все уведомления и задачи — только в кабинете, без почты, SMS и звонков. Срок решения банка не обещается |
| **BR-16** | **Допустимые действия.** Отозвать заявку можно только в `SUBMITTED` и `SPECIALIST_REVIEW`. Действие не в своём статусе система отклоняет |

## Описания вариантов использования
 
### UC-00. Получить финансирование под задачу бизнеса 
 
| Поле | Значение |
| --- | --- |
| **Контекст** | Объединяет все цели предпринимателя от потребности до денег или понятного плана. Показывает, как связаны варианты уровня |
| **Основной актор** | Предприниматель |
| **Область** | Умный кредитный кабинет |
| **Предусловия** | У бизнеса есть операционная задача: оплата поставщику, сезонная закупка, кассовый разрыв |
| **Минимальные гарантии** | Данные не теряются между сессиями. Кредитная история не затрагивается до осознанной подачи |
| **Гарантии успеха** | Деньги на счёте (`DISBURSED`) или маршрут, после которого клиент понимает, что делать и когда возвращаться |
 
**Основной сценарий**
1. Предприниматель узнаёт шансы и условия до подачи — UC-01.
2. Предприниматель подаёт заявку — UC-02.
3. Предприниматель получает решение банка — UC-03.
4. Предприниматель принимает предложение и получает деньги — UC-04. Конец.
**Расширения**
- **1а.** Шанс низкий из-за стоп-фактора: предприниматель проходит маршрут без подачи — UC-07, затем возвращается к шагу 1.
- **3а.** Иные условия: UC-05.
- **3б.** Нужны данные: UC-06, затем шаг 3.
- **3в.** Отказ: UC-07, затем новая заявка с шага 1.
- **3г.** Приостановка по 115-ФЗ: процедура пересмотра вне кредитного процесса. Конец.
- **3д.** Заявка ушла к специалисту: UC-10 со стороны банка, затем шаг 3.
- **\*а.** В любой момент до решения предприниматель отзывает заявку — UC-08.

### UC-01. Узнать шансы и условия до подачи заявки 
 
| Поле | Значение |
| --- | --- |
| **Контекст** | Сегодня единственный способ узнать сумму — подать заявку и рискнуть отказом. Здесь клиент видит шанс, сумму и стоимость заранее и решает, подавать ли |
| **Основной актор** | Предприниматель |
| **Вспомогательные акторы** | Реестры, счёт в банке, ФНС, ФССП, арбитраж (моки) |
| **Область** | Кабинет: шаги «Цель», «Компания», «Финансы», «Предложение» |
| **Заинтересованные лица** | Предприниматель — не испортить кредитную историю. Банк — реалистичная сумма на входе. Комплаенс — оценка не выглядит решением |
| **Предусловия** | Предприниматель вошёл в кабинет (UC-S1). У учётки одна компания с ИНН |
| **Триггер** | Клиент нажимает «Подобрать кредит» или «Новая заявка» |
| **Минимальные гарантии** | Введённое сохранено в черновике `DRAFT`. Запроса в БКИ не было. Заявка не подана |
| **Гарантии успеха** | Клиент видит предоценку с подписью по BR-01 и выбрал вариант. Предоценка сохранена в черновике и действует 30 дней |
 
**Основной сценарий**
1. Клиент описывает задачу своими словами, например «нужно 850 тыс. на закупку к сезону».
2. Система распознаёт цель, сумму и срок, предлагает продукт по BR-03: оборотный кредит или овердрафт («запас на месяц» → овердрафт) и показывает распознанные поля.
3. Клиент проверяет поля и подтверждает продукт.
4. Система сохраняет черновик `DRAFT`, подставляет компанию по ИНН из учётки и подтягивает ОКВЭД, возраст бизнеса, обороты за 6 мес., срок обслуживания счёта, долг бизнеса, данные ФНС, ФССП и судов.
5. Клиент подтверждает: «Да, это моя компания».
6. Клиент указывает выручку и отвечает на два вопроса о себе: просрочки за 2 года, включая закрытые; личные платежи и загрузка кредитных карт.
7. Система помечает ответы о владельце «со слов клиента, проверим после подачи» по BR-01 и сохраняет черновик.
8. Система считает предоценку той же моделью, что и решение, по BR-02 — BR-06, без запроса в БКИ.
9. Система показывает шанс, вилку доступной суммы, платёж и полную стоимость в рублях, причины с цветом и подпись по BR-01, формирует 1–3 варианта: запрошенная сумма, сумма в пределах оценки, другой срок, другой продукт.
10. Клиент выбирает вариант. Дальше — UC-02.
**Расширения**
- **1а.** Помощник не распознал фразу или языковая модель недоступна (BR-11):
  - 1а1. Система показывает форму из трёх полей: цель, сумма, срок.
  - 1а2. Клиент заполняет форму. Переход к шагу 3.
- **2а.** Распознаны не все поля: система спрашивает только недостающие. Переход к шагу 3.
- **2б.** Клиент смотрит, какие ещё продукты есть: система показывает остальные продукты с пометкой «скоро» `[доработка]`; в MVP доступны оборотный кредит и овердрафт. Переход к шагу 3.
- **3а.** Клиент исправляет распознанные поля: система сохраняет исправления. Переход к шагу 4.
- **4а.** Компания не найдена в реестрах:
  - 4а1. Система сообщает «компания не найдена».
  - 4а2. Клиент заполняет данные компании вручную. Переход к шагу 6.
- **6а.** Клиент пропускает шаг «Финансы»: система считает по оборотам счёта. Переход к шагу 8.
- **9а.** Шанс высокий, сумма в пределах оценки (P1): блок «что влияет» не показывается. Переход к шагу 10.
- **9б.** Сумма выше оценки (P2): система показывает вариант «в пределах оценки» и причину «сумма велика для вашего оборота». У P2 вилка 2 550 000 – 2 850 000 ₽.
- **9в.** Сработал стоп-фактор (P3, налоговая задолженность):
  - 9в1. Система показывает низкий шанс и прямо пишет, что уменьшение суммы стоп-фактор не снимает.
  - 9в2. Система предлагает три действия: изменить сумму или срок; открыть маршрут без подачи `[доработка]`; подать всё равно.
  - 9в3. Клиент выбирает маршрут без подачи — UC-07 (расширение 1а); или подачу — UC-02 (расширение 5а); или изменение — шаг 10а.
- **9г.** Сработал постоянный стоп-фактор (BR-05): система показывает, что продукт для компании недоступен, и причину. Маршрута к этому продукту нет. Конец.
- **9д.** Банк видит не весь оборот (P5): система показывает потолок по видимому обороту (220 000 ₽ у P5) и подсказку «часть оборота не видна банку — можно подтвердить выпиской».
- **9е.** Данные о владельце со слов клиента (P4): система показывает пометку «кредитную историю проверим после подачи — результат может измениться».
- **10а.** Клиент меняет сумму или срок: система пересчитывает предоценку. Переход к шагу 9.
- **10б.** Клиент уходит из кабинета: черновик сохранён; при возврате система предлагает «Продолжить с шага N».
- **10в.** С расчёта прошло больше 30 дней: система помечает предоценку устаревшей и пересчитывает при входе. Переход к шагу 9.
- **10г.** Клиент удаляет ненужный черновик `[доработка]`: система просит подтверждение и удаляет черновик. Конец.
**Отображаемые данные**
 
| Где | Что видит клиент | Зачем |
| --- | --- | --- |
| Шаг «Цель» | Распознанные цель, сумма, срок, продукт | Проверить, что система поняла задачу |
| Шаг «Компания» | Название, ИНН, ОКВЭД, возраст бизнеса, средний оборот | Подтвердить, а не вводить заново |
| Шаг «Предложение» | Шанс, «текущая высота» (вилка суммы), «вершина» (запрошенная сумма), платёж, полная стоимость в ₽, причины с цветом 🟢 / 🟡 / 🔴, пометка о словах клиента, подпись BR-01 | Решить, подавать ли и на какую сумму |
| Варианты | Сумма, срок, ставка, платёж, переплата, метка «★ Лучший вариант» | Выбрать вариант |

### UC-02. Подать заявку на финансирование 
 
| Поле | Значение |
| --- | --- |
| **Контекст** | Клиент решил подавать. Нужно собрать только недостающее, получить согласия и запустить обработку |
| **Основной актор** | Предприниматель |
| **Область** | Кабинет: шаги «Документы» и «Отправка» |
| **Заинтересованные лица** | Предприниматель — не собирать лишние бумаги. Банк — полные данные и согласия до обработки |
| **Предусловия** | Черновик с выбранным вариантом и предоценкой (UC-01) |
| **Триггер** | Клиент выбрал вариант и нажал «Дальше» |
| **Минимальные гарантии** | Без двух согласий заявка не уходит. Неотправленный черновик сохранён |
| **Гарантии успеха** | Заявка зарегистрирована: `DRAFT` → `SUBMITTED` → `IN_REVIEW`. Каждое изменение статуса записано в журнал событий. Клиент видит ленту этапов |
 
**Основной сценарий**
1. Система показывает чек-лист только недостающих документов.
2. Клиент загружает недостающее.
3. Система показывает сводку заявки.
4. Клиент проверяет сводку и даёт два согласия: на запрос в БКИ и на обработку данных.
5. Клиент отправляет заявку.
6. Система проверяет обязательные поля и согласия, регистрирует заявку `DRAFT` → `SUBMITTED` → `IN_REVIEW` и пишет переходы в журнал.
7. Система показывает ленту этапов проверки Б1–Б4 и не называет срок решения (BR-15). Дальше — UC-03.
**Расширения**
- **1а.** У клиента расчётный счёт в банке (P1): чек-лист пуст, «документы не нужны». Переход к шагу 3.
- **2а.** Клиент заранее прикладывает выписку второго банка: проверка её учтёт. Переход к шагу 3.
- **4а.** Не отмечены оба согласия: кнопка отправки неактивна. Остаётся шаг 4.
- **4б.** Клиент нажимает «Изменить» в сводке: система открывает нужный шаг UC-01 с сохранёнными данными; после правки — переход к шагу 3.
- **5а.** Предоценка низкая из-за стоп-фактора (UC-01, 9в):
  - 5а1. Система требует подтвердить предупреждение «заявка будет видна в кредитной истории».
  - 5а2. Клиент подтверждает — переход к шагу 6; отказывается — возврат к UC-01, шаг 10.
**Отображаемые данные:** список недостающих документов и их статусы; сводка — компания, цель, продукт, сумма, срок, платёж, полная стоимость; тексты двух согласий; лента этапов.

### UC-03. Получить решение банка по заявке 
 
| Поле | Значение |
| --- | --- |
| **Контекст** | Клиент ждёт решение и должен понимать, что происходит и что делать дальше. Решение принимают правила, человек — только в исключениях |
| **Основной актор** | Предприниматель |
| **Вспомогательные акторы** | Счёт в банке, реестры, ФНС, ФССП, БКИ, платформа ЗСК (моки); кредитный специалист — в исключениях |
| **Область** | Кабинет: экран «Статус» |
| **Заинтересованные лица** | Банк — максимум решений без человека, прослеживаемость. Комплаенс — 115-ФЗ не смешан с кредитным отказом. Недобросовестный заявитель *(негативное)* — данные проверяются до решения |
| **Предусловия** | Заявка в статусе `IN_REVIEW` (UC-02) |
| **Триггер** | Регистрация заявки |
| **Минимальные гарантии** | Заявка не теряется: при сбое уходит специалисту. Клиент всегда видит текущий статус. Приостановка по 115-ФЗ не показывается как кредитный отказ |
| **Гарантии успеха** | Клиент видит исход с причиной и следующим действием. Решение и причина записаны в журнал |
 
**Основной сценарий**
1. Система проверяет полноту и сверяет заявленную выручку с оборотом по счёту (Б1).
2. Система запрашивает кредитную историю владельца в БКИ и уровень риска по 115-ФЗ (Б2).
3. Система считает оценку на проверенных данных: БКИ вместо слов клиента (Б3).
4. Система выносит решение по правилам BR-06 без участия человека (Б4).
5. Система показывает одобрение `APPROVED`: сумму, ставку, платёж, полную стоимость в рублях и срок действия предложения по BR-14. У P1 — 850 000 ₽ на 24 мес., 43 261 ₽ в месяц, полная стоимость 196 774 ₽.
6. Клиент читает решение. Дальше — UC-04.
**Расширения**
- **1а.** Заявленная выручка выше оборота больше чем на 30% или не хватает документа (BR-07, P5): система переводит заявку в `INFO_REQUESTED` и показывает, что нужно и до какой даты. Дальше — UC-06.
- **2а.** Уровень риска по 115-ФЗ красный (BR-10, ZSK): система переводит заявку в `SUSPENDED_115FZ`, показывает шаблонный текст и порядок пересмотра со ссылками на cbr.ru. Маршрута нет. Конец.
- **2б.** Кредитная история по БКИ хуже, чем со слов клиента (P4): система считает по данным БКИ; исход может отличаться от предоценки. Переход к шагу 4.
- **4а.** Сработал триггер специалиста (BR-08, P2 — `AMOUNT_ABOVE_2M`):
  - 4а1. Система переводит заявку в `SPECIALIST_REVIEW`, сохраняет свой исход как рекомендацию.
  - 4а2. Клиент видит «Заявку рассматривает специалист», срок не называется; до решения может отозвать заявку (UC-08).
  - 4а3. Специалист выносит решение (UC-10). Переход к шагу 5 или к расширениям 5а–5в.
- **4б.** Движок оценки недоступен после трёх попыток: система переводит заявку в `SPECIALIST_REVIEW` с триггером `ML_UNAVAILABLE`. Переход к 4а2.
- **5а.** Иные условия `COUNTER_OFFER`: система показывает «Хотели X — можем Y», что ограничивает сумму, платёж и стоимость. У P2 — 2 850 000 ₽ из 3 000 000 ₽, 184 575 ₽ в месяц, 500 852 ₽, ограничивает оборот (`L_TURNOVER`). Дальше — UC-05.
- **5б.** Отказ `REJECTED`: система показывает причины по BR-09 простыми словами и ближайшую альтернативу, строит и сохраняет маршрут. У P3 — 53 балла, главная причина «налоговая задолженность 86 000 ₽», всего пять причин; у P4 — «просрочка 90+ дней за последние 12 месяцев». Дальше — UC-07.
- **5в.** Отказ по постоянному стоп-фактору: система показывает причину; маршрута к этому продукту нет. Конец.
- **5г.** Языковая модель недоступна или её текст не прошёл проверку (BR-11): показан шаблонный текст. Переход к шагу 6.
- **6а.** Клиент не согласен с причиной `[доработка]`: нажимает «Не согласен с причиной», система добавляет триггер `CLIENT_DISPUTE` и передаёт заявку специалисту. Переход к 4а1.
**Отображаемые данные**
 
| Исход | Что видит клиент |
| --- | --- |
| Ожидание | Лента событий Б1–Б4, срок не называется |
| `SPECIALIST_REVIEW` | «Заявку рассматривает специалист», кнопка «Отозвать заявку» |
| `APPROVED` | Сумма, ставка, платёж, полная стоимость, срок действия |
| `COUNTER_OFFER` | Запрошенная и предложенная сумма рядом, что ограничивает, платёж, стоимость |
| `INFO_REQUESTED` | Какой документ, до какой даты, кнопка загрузки |
| `REJECTED` | Причины, первая — главная; альтернатива; блок «Следующий привал» со ссылкой на маршрут |
| `SUSPENDED_115FZ` | Шаблонный текст «это не оценка кредитоспособности», порядок пересмотра, без маршрута и баллов |

- **3б.** Клиент отказывается подписывать договор `[доработка]`: система переводит заявку в `DECLINED_BY_CLIENT`. Конец.
**Отображаемые данные:** сумма, срок, платёж, полная стоимость; для овердрафта — лимит, проценты при полном использовании и комиссия за установку; история переходов «принял → подписан → перечислены».

### UC-07. Пройти маршрут к одобрению 
 
| Поле | Значение |
| --- | --- |
| **Контекст** | Объяснения причины мало: клиенту нужно понять, что исправить, за какой срок и как это меняет оценку. Без исправления причины повторная попытка ведёт к повторному отказу |
| **Основной актор** | Предприниматель |
| **Область** | Кабинет: страница «Маршрут к одобрению» (см. [route-pages.md](route-pages.md)) |
| **Заинтересованные лица** | Предприниматель — путь и момент возврата. Банк — отказник возвращается в этот же банк с изменившимися данными. Комплаенс — срок не выглядит обещанием |
| **Предусловия** | Маршрут есть: после `REJECTED`, после `DECLINED_BY_CLIENT` или по черновику из предоценки `[доработка]`. При `SUSPENDED_115FZ` маршрута нет |
| **Триггер** | Клиент открывает маршрут |
| **Минимальные гарантии** | Маршрут и отметки сохраняются между входами. Пересчёт не создаёт заявку и не обращается в БКИ. Срок подан как ориентир (BR-12) |
| **Гарантии успеха** | Маршрут дошёл до `READY`, клиент создал новую заявку; либо, если быстрого пути нет, клиент знает срок, что делать сейчас и чего не делать |
 
**Основной сценарий**
1. Клиент открывает страницу «Маршрут к одобрению».
2. Система показывает, что держит результат, причины с цветом, горизонт («Следующий привал»), шаги — действие, срок, вклад в баллы, — прогноз, предупреждения и подпись по BR-12. У P3: погасить сальдо ЕНС (+0, снимает стоп) → снизить загрузку кредиток ниже 50% (+8) → вести всю выручку через один счёт (+12), горизонт «~3 мес.».
3. Клиент выполняет шаг вне кабинета и отмечает его.
4. Система пересчитывает прогноз той же моделью, сохраняет отметки, обновляет горизонт и карту. У P3 после двух шагов — 61 балл, остаётся «вся выручка через один счёт».
5. Шаги 3–4 повторяются, пока маршрут не получит `READY` по BR-13.
6. Система показывает «Готов к подаче» и кнопку «Подать новую заявку».
7. Клиент нажимает кнопку; система создаёт новый черновик с данными маршрута. Дальше — UC-01 с шага 9. У P3 прогноз — 77 баллов, 1 100 000 ₽ из 1 200 000 ₽, иные условия, полная стоимость 254 649 ₽.
**Расширения**
- **1а.** Маршрут без подачи `[доработка]`: система строит маршрут по черновику на данных предоценки, данные о владельце со слов клиента, без запроса в БКИ; заявка остаётся в `DRAFT`. Переход к шагу 2.
- **2а.** Держит временное окно (`TIME_WINDOW`, P4):
  - 2а1. Система показывает «~8 мес., ускорить нельзя» и шаг «дождаться» без отметки.
  - 2а2. Система показывает, что делать сейчас (закрыть производство ФССП, вести выручку через счёт) и чего не делать: «Не подавайте заявки в другие банки — каждая заявка видна в кредитной истории и снижает рейтинг на 2–3 месяца». Без анимации и игровых элементов. Конец.
- **2б.** Держит оборот (`TURNOVER`, P2): один шаг — рост оборота до целевого уровня; система пишет, что сумму держит оборот, а не баллы. Переход к шагу 3.
- **2в.** Маршрут построен по решению специалиста: система показывает «Маршрут построен по решению специалиста банка». Переход к шагу 3.
- **3а.** Клиент снимает отметку: система пересчитывает прогноз. Переход к шагу 4.
- **4а.** Отмечены не все шаги: прогноз растёт частично, порог не достигнут, кнопки новой заявки нет `[доработка]: сейчас «Новая заявка» доступна всегда`. Переход к шагу 3.
- **4б.** Шаг меняет кредитную историю: система показывает, что бюро обновит данные за 2 рабочих дня. Переход к шагу 5.
- **5а.** Клиент уходит: прогресс сохранён и показывается при следующем входе.
**Отображаемые данные:** карта-гора (текущая высота, вершина, препятствие), «что мешает» с цветами, горизонт, шаги с отметками, прогноз суммы, предупреждения «чего не делать», подпись BR-12, кнопка «Подать новую заявку» при `READY`.

| **Триггер** | Клиент открывает «Помощь» |
| **Минимальные гарантии** | В ответе нет чисел и кодов, которых нет в заявке, и нет «одобрено» до решения (BR-11) |
| **Гарантии успеха** | Клиент получил ответ по своей заявке или объяснение термина |
 
**Основной сценарий**
1. Клиент открывает «Помощь».
2. Система показывает подсказки-вопросы по стадии заявки.
3. Клиент выбирает или пишет вопрос, например «Почему отказали?».
4. Система отвечает по фактам заявки шаблоном.
5. Система заменяет шаблон переформулировкой языковой модели, если та прошла проверку по BR-11. Конец.
**Расширения**
- **3а.** Вопрос о термине («Что такое сальдо ЕНС?»): система отвечает из словаря. Конец.
- **3б.** Вопрос не по теме: система отвечает, с чем помогает, и предлагает примеры вопросов. Переход к шагу 3.
- **4а.** Заявка приостановлена по 115-ФЗ: только шаблон, языковая модель не привлекается. Конец.
- **5а.** Модель недоступна или её текст не прошёл проверку: остаётся шаблон. Конец.

### UC-10. Рассмотреть заявку-исключение 
 
| Поле | Значение |
| --- | --- |
| **Контекст** | Скоринг ≠ решение. Нестандартные заявки разбирает человек на готовом досье, а клиент получает решение и маршрут, согласованные с ним |
| **Основной актор** | Кредитный специалист |
| **Область** | Кабинет специалиста: очередь, досье, решение |
| **Заинтересованные лица** | Банк — прослеживаемость. Предприниматель — решение специалиста объяснимо так же, как автоматическое |
| **Предусловия** | Специалист вошёл (UC-S1, логин `specialist`). Заявка в `SPECIALIST_REVIEW` |
| **Триггер** | В очереди появилась заявка |
| **Минимальные гарантии** | Решение не сохраняется без кода причины. Каждое действие записано в журнал |
| **Гарантии успеха** | Заявка получила исход; клиент видит решение и маршрут, построенный от решения специалиста |
 
**Основной сценарий**
1. Специалист открывает очередь.
2. Система показывает заявки с причиной попадания (триггер по BR-08).
3. Специалист открывает досье.
4. Система показывает проверки Б1–Б2, 9 факторов с баллами, компоненты лимита с подсветкой ограничивающего, лимиты по продуктам, стоп-факторы и рекомендацию системы. У P2 — 72 балла, оборотный кредит 2 850 000 ₽ и овердрафт 760 000 ₽ при тех же баллах.
5. Специалист подтверждает рекомендацию, выбирает код причины из справочника и пишет комментарий. У P2 — «Иные условия», `L_TURNOVER`.
6. Специалист сохраняет решение.
7. Система переводит заявку в итоговый статус, пишет в журнал, кто, когда, из какого статуса, с каким кодом и комментарием, и строит маршрут от решения специалиста. Конец.
**Расширения**
- **3а.** Клиент отозвал заявку: она уходит из очереди. Конец.
- **5а.** Специалист выбирает другой исход: одобрить, запросить данные или отказать → `APPROVED`, `INFO_REQUESTED` или `REJECTED`. Переход к шагу 6.
- **6а.** Код причины не выбран: кнопка сохранения неактивна. Возврат к шагу 5.
**Отображаемые данные:** очередь с триггером и временем ожидания; досье с факторами (`points` / `max_points`), лимитами по компонентам, стопами и рекомендацией; справочник кодов причин; журнал действий.
