# Smart Credit для банка: внедрение и требования enterprise

Как прототип переносится в банковский контур и как он отвечает критерию кейса «Enterprise-ориентированность».

## 1. Как внедрить в банке

Скоринг здесь — явная балльная карта на правилах (`ml/config/policy.yaml`), а не «чёрный ящик»: так требуют
объяснимость для клиента и прослеживаемость решений для специалиста. Веса подобраны под синтетические данные; на
синтетике карта различает заёмщиков с Gini 0,46 и стабильна ([docs/model-validation.md](model-validation.md)).

| Что банк меняет | Что остаётся как есть |
|---|---|
| Веса, пороги, продукты и ставки — в `ml/config/*.yaml`, без правки кода | Маршрут к одобрению: шаги клиента, сроки, «ускорить нельзя», пересчёт |
| Калибровка: `python -m validation.run` на своей истории заявок вместо синтетики → предложенные веса | Единый справочник причин: код → текст клиенту → шаг → срок |
| Моки реестров и БКИ → реальные интеграции в бэкенде | Объяснения и помощник на локальной LLM с проверкой каждого ответа; 115-ФЗ — только шаблон |
| Модель LLM — любая с открытыми весами (`OLLAMA_MODEL`) | Одна модель для предоценки, решения и маршрута: прогноз не расходится с решением |

## 2. Требования банковской разработки

Критерий кейса «Enterprise-ориентированность»: безопасность, надёжность, отказоустойчивость, масштабирование и сопровождение.

| Требование | Как сделано в прототипе | Где смотреть | Что было бы в банке |
|---|---|---|---|
| Доступ и роли | JWT с ролью; роль проверяется на каждом эндпоинте: клиент видит только свою компанию, специалист — очередь и досье, админ — состояние и сброс демо | `backend/app/api/deps.py`, `backend/app/api/*` | Вход через корпоративный SSO, срок жизни токенов по политике банка |
| Пароли и секреты | Пароли — bcrypt; секреты только через `.env` (в Git — `.env.example`); служебный токен между бэкендом и ML (`ML_SERVICE_TOKEN`) | `backend/app/services/auth.py`, `.env.example` | Хранилище секретов (Vault), mTLS между сервисами |
| Изоляция | Контейнеры backend и ml работают не от root; на сервере наружу открыт только сайт через Caddy с HTTPS, backend, ml, llm и база — во внутренней сети | `backend/Dockerfile`, `ml/Dockerfile`, `docker-compose.prod.yml` | WAF и сетевые политики периметра банка |
| Персональные данные | Все данные синтетические; в журнал запросов пишутся только id запроса, метод, путь и статус — без ИНН и сумм; в LLM уходят тексты из кодов причин, а не данные заявки | `ml/service/observability.py`, [ml/README.md](../ml/README.md#локальная-llm) | Маскирование ПДн в логах и интерфейсе по стандарту банка |
| Целостность статусов | Смена статуса и запись события — одним коммитом в базе; недопустимый переход отвечает `409`; повторная подача отправленной заявки не проходит | `backend/app/services/applications.py` | Ключи идемпотентности на изменяющих запросах |
| Отказоустойчивость | Вызовы ML с таймаутом и до 3 попыток; если ML недоступен, заявка уходит к специалисту (`ML_UNAVAILABLE`), а не теряется; без LLM всё работает на шаблонах | `backend/app/services/ml.py`, `backend/app/services/pipeline.py` | Circuit breaker и резервный экземпляр движка |
| Масштабирование | backend и ml без состояния, состояние — в PostgreSQL; индексы по статусу, компании и заявке; этапы конвейера — фоновые задачи | `backend/app/db/models.py`, [docs/architecture.md](architecture.md) | Очередь этапов (Kafka / RabbitMQ) с повторами, несколько экземпляров за балансировщиком |
| Аудит и трассируемость | Каждое событие заявки — кто, когда, что; у решения движка — версия политики, версия движка, хэш входа, время; решение специалиста — только с кодом причины; сквозной `X-Request-ID` | `ApplicationEvent`, `audit` в ответах ML, [docs/api-contract.md](api-contract.md) | Отдельное неизменяемое хранилище журнала аудита |
| Наблюдаемость | `/health` и healthcheck у каждого сервиса, метрики Prometheus у движка (`GET ml:8001/metrics`), журнал ML в JSON | `docker-compose.yml`, `ml/service/observability.py` | Prometheus + Grafana, централизованные логи, алерты |
| Объяснимость и управление моделью | Балльная карта на правилах; веса, пороги и продукты — в `policy.yaml` без правки кода; проверка модели: различение, стабильность, калибровка | `ml/config/`, [docs/model-validation.md](model-validation.md) | Утверждение политики кредитным комитетом, мониторинг модели на реальной истории |
| Сопровождение | OpenAPI для backend и ML с тестами свежести; миграции Alembic; тесты ML, backend и фронта; CI на каждый пуш, включая миграции на PostgreSQL; коллекция Postman | `docs/openapi-*.{json,yaml}`, `backend/app/migrations/`, `.github/workflows/tests.yml` | Тот же контур в CI/CD банка, контрактные тесты с внешними системами |
| Воспроизводимость и независимость | Один `docker compose up` на обычном ПК; lock-файлы и образы с зафиксированными версиями; LLM с открытыми весами работает локально, платных API и подписок нет | `uv.lock`, `package-lock.json`, `Dockerfile`, [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md) | Внутренний реестр образов и зависимостей банка |
